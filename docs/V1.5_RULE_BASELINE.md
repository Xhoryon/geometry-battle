## 3. Exact Emitter classification

### 3.1 Formal match semantics

The real sequence is:

```text
upload/seal both packages → decoy preflight → generate match map
→ EMITTER_SELECT → each team selects an initial point → each team locks
→ remove both selected points from combat points → READY
```

The Emitter is fixed **within that match**, cannot be killed, and is not counted toward victory. Initial point IDs remain stable; selecting one does not renumber the remaining points.

[Match.ts:727–734](../src/core/Match.ts#L727-L734) supplies the selected coordinates to round input, function validation and shot resolution. Formal input calls explicitly provide Emitter values; they do not rely on the legacy default.

### 3.2 Why ±18 is neither dead code nor the current combat rule

[MapGenerator.ts:276–298](../src/map/MapGenerator.ts#L276-L298) still uses fixed `EMITTERS` to reserve map layout space. [MapGenerator.ts:430–453](../src/map/MapGenerator.ts#L430-L453) checks their obstacle/point clearance. [MapGenerator.ts:366–377](../src/map/MapGenerator.ts#L366-L377) includes map Emitter fields in the map hash.

These are active map-generation/validation/hash constraints. Removing or changing them changes generated maps or hashes, so deletion is **not** a no-rule-diff cleanup.

[InputProtocol.ts:78–114](../src/core/InputProtocol.ts#L78-L114) also retains an optional legacy fallback. Numerous low-level test fixtures use it. Formal Match and local tools explicitly pass selected/decoy anchors. Decoy preflight uses selected points from the decoy map, not universally the ±18 constants.

**Answer to the Master Plan's A/B/C/D question:** different uses coexist, with stale comments. Official Web combat uses participant-selected per-match anchors; legacy constants still affect layout, hashing and default tooling. [Rules.ts:20–31](../src/core/Rules.ts#L20-L31)'s “not chosen by anyone” explanation is stale. This is not a finding that all matches still fire from ±18.

### 3.3 Entry-point discrepancy

[operator/judge.ts:355–361](../src/operator/judge.ts#L355-L361) and [operator/cli.ts:264–266](../src/operator/cli.ts#L264-L266) call `autoSelectEmitters()` even on non-automatic paths. The helper chooses the first candidate for each team and locks both. Its own [contract](../src/core/Match.ts#L691-L709) reserves that behavior for unattended rehearsal/tests.

An audit-only invocation of the interactive judge, using new temporary slots and input `v`, `s`, `q`, without `--auto` or supplied packages, seeded the slots and reached READY. The equivalent Web preparation reached EMITTER_SELECT. This confirms a preparation/decision-right difference, not a second combat implementation.

## 4. Timing, result acceptance and round completion

### Timing authority

- Start: each team's own monotonic timestamp immediately **after** its GO pipe write, [SandboxRunner.ts:1079–1104](../src/runner/SandboxRunner.ts#L1079-L1104).
- Successful finish: result file mtime mapped into monotonic time; an unusable/out-of-budget mtime falls back to host observation time, [SandboxRunner.ts:1007–1017](../src/runner/SandboxRunner.ts#L1007-L1017).
- Result: the first observed envelope passing the result schema is retained; later file versions are not reconsidered. DSL validity is evaluated later in Match.
- Process exit/drain grace is not normally charged after result acceptance.
- Countdown is synchronous engine progression, not a real three-second sleep.
- Browser timers, animations and RoundMachine wall-clock history do not adjudicate computation time.

### Confirmed deadline gap

A harmless solver sleeping 650 ms under a 500 ms budget was rejected normally with `TIMEOUT`. With only the probe host's event loop paused for 1000 ms, the same solver was accepted with `success=true` and `computeTimeMs=1005.4385`.

The late poll sets `pendingResult` and cancels the timeout without requiring the selected timestamp to satisfy the deadline. [Match.ts:997–1007](../src/core/Match.ts#L997-L1007) adds no time rejection; [LocalPreflight.ts:256–266](../src/submission/LocalPreflight.ts#L256-L266) does. The test simulates a stalled host; it does **not** claim that a contestant can always cause this stall. The enforcement discrepancy is nevertheless real.

The temporary-file write mtime is also not identical to atomic-rename visibility. Existing public README text explicitly names mtime. Choosing another endpoint would require a timing-contract decision, not a silent audit fix.

### What ends a round

Both Runners settle, both outputs are parsed/validated, all valid attacks resolve, deaths and the no-progress streak update, and round/replay records are created. Only then are START authorization and cached round inputs cleared. The engine reaches READY or MATCH_END. First output, first hit or elimination during the first attack does not by itself end the round.

### What ends a match

After all attacks in the round:

1. Single-side elimination: surviving side wins; mutual elimination: draw.
2. Otherwise, 20 zero-kill rounds: stalemate draw.
3. Otherwise, round 60: hard-limit draw.

The engine still ends **by** its hard limit. The inaccurate statement is “round 60 always overrides a same-round elimination with DRAW.” CLI early stopping is a separate operator behavior. No claim is made that arbitrary platform crashes or stalled hosts have a bounded total match wall-clock duration.

## 5. Geometry and numerical rule boundaries

### Confirmed circle-contact defect

Synthetic case, using the unchanged canonical parser, Validator and Judge:

- Circle center `(0,0)`, radius `1`.
- `f(x)=x+sqrt(2)-1e-6`.
- A Emitter `(-6,f(-6))`; live B point `(6,f(6))`.
- Independent center-to-line distance is `0.9999992928932189 < 1`: the line crosses the circle.
- Validator returned valid; Judge returned no obstacle and killed `B1`.
- Control `f(x)=x+sqrt(2)-0.1` was correctly blocked and killed no point.

[Judge.ts:113–164](../src/core/Judge.ts#L113-L164) samples a fixed 128 intervals across each obstacle projection. A narrow intersection can fall between samples; bisection runs only after a sample is inside. Rendering's adaptive trace step does not repair that search. The actual crossing control avoids relying solely on floating-point interpretation of exact tangency.

This is a demonstrated low-level combat-rule defect, not a measured prevalence across generated tournament maps. Existing obstacle and mirror suites still pass: symmetry tests can preserve the same error on both sides.

### Qualifications that should survive specification freezing

- Continuity, C² and convexity checks are numerical checks, not analytical proofs over every real x.
- Validator samples from the Emitter toward the far side. With non-integral `span/h`, the last grid point is not necessarily the exact far endpoint.
- Central differences can evaluate just outside the attack interval. “The platform never evaluates outside the interval” is too strong.
- Geometry primitives support four obstacle types; official generation/input currently uses rectangles and circles. Lower-level support is not automatically an official input contract.

## 6. Existing bilateral resolution and R4 implications

Locked Attack Right already ensures both valid attacks execute, including mutual elimination. A attacks B's points; B attacks A's points. The first attack does not remove the second attack's enemy target set. Existing AB/BA/tie order-independence tests passed in this audit.

Therefore, “both sides get to attack” or “mutual elimination is a draw” is **not** the new R4 experiment. A future experiment must specify its actual delta: removing initiative metadata, always applying one frozen snapshot, changing timing's competitive role, or introducing an official seed. No such change is adopted here. The official deterministic solver-seed contract, ruleset ID and protocol version decisions remain future work; existing map seeds are a separate, already implemented concept.

Actual code is [Validator.ts:230–246](../src/core/Validator.ts#L230-L246), with an Emitter-anchored directional grid, and [mirror-helpers.ts:31–33](../tests/mirror-helpers.ts#L31-L33), [mirror-fairness.ts](../tests/mirror-fairness.ts) and [mirror-match.ts](../tests/mirror-match.ts).

This finding does not establish new slot bias or invalidate the measured results of an independently evidenced campaign. It does mean that the active public report is not reliable evidence for its described implementation/campaign. Its stated 30-map/60-match statistics were **not independently reproduced** here. Historical reports and released files were not rewritten.
