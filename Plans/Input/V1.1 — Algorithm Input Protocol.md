# V1.1 — Algorithm Input Protocol

## 1. 总体结构

每一轮比赛的数据分成两部分：

```text
PUBLIC STATE
    +
REVEAL STATE
    +
START SIGNAL
```

对应：

```text
public_state.json
reveal_state.json
START
```

两个 JSON 都准备完成以后，算法仍然不能运行。

只有裁判点击：

```text
START ROUND
```

之后，两支算法才同时进入正式计算阶段。

---

# 2. 为什么拆成两个 JSON

比赛本身存在两个信息阶段。

## Stage A — 揭盲前

双方已经知道：

- 当前 Round；
- 地图坐标范围；
- 所有点的位置；
- 点编号；
- 点属于哪一方；
- 哪些点仍然存活。

但不知道：

- 本轮隐藏障碍物；
- 对方选择的 Shooter；
- 最终完整 Round State。

这些信息组成：

```text
public_state.json
```

---

## Stage B — 揭盲

双方 Shooter 已经锁定。

系统揭示：

- Team A Shooter；
- Team B Shooter；
- 本轮所有障碍物；
- 障碍物精确数学参数。

这些信息组成：

```text
reveal_state.json
```

---

## Stage C — START

两个 JSON 均冻结后：

```text
WAITING FOR JUDGE
```

裁判点击：

```text
START
```

才允许 Algorithm Runner 真正开始运行。

---

# 3. 一轮完整流程

正式 Round 流程：

```text
ROUND N
   ↓
Generate public_state.json
   ↓
Display Points
   ↓
Human Shooter Selection
   ↓
Team A LOCK
Team B LOCK
   ↓
REVEAL
   ↓
Generate reveal_state.json
   ↓
Display Shooters + Obstacles
   ↓
WAITING FOR JUDGE
   ↓
Judge clicks START
   ↓
Freeze both JSON files
   ↓
Launch / release Team A Runner
Launch / release Team B Runner
   ↓
Algorithms read both JSONs
   ↓
Compute
   ↓
Return Function DSL
```

注意：

```text
REVEAL
```

和：

```text
START
```

是两个不同事件。

这可以让现场出现：

```text
Shooter Reveal
Obstacle Reveal

...

START!
```

的比赛节奏。

该文件必须在揭盲前即可公开。

建议格式：

```json
{
  "schema_version": "1.1",
  "match_id": "MATCH-001",
  "round": 4,

  "map": {
    "xmin": -20,
    "xmax": 20,
    "ymin": -12,
    "ymax": 12
  },

  "points": [
    {
      "id": "A1",
      "team": "A",
      "x": -14,
      "y": 6,
      "alive": true
    },
    {
      "id": "A2",
      "team": "A",
      "x": -10,
      "y": -3,
      "alive": false
    },
    {
      "id": "B1",
      "team": "B",
      "x": 9,
      "y": 5,
      "alive": true
    },
    {
      "id": "B2",
      "team": "B",
      "x": 16,
      "y": -1,
      "alive": true
    }
  ]
}
```

---

# 5. public_state 中应该包含什么

建议包含：

### Match identification

```text
schema_version
match_id
round
```

### Map

```text
xmin
xmax
ymin
ymax
```

### Points

每个点：

```text
id
team
x
y
alive
```

---

# 6. public_state 不应该包含什么

绝对不能包含：

```text
obstacles
obstacle count
obstacle type
obstacle coordinates
hidden map seed
future Round data
opponent Shooter
```

特别注意：

## 不公开 Map Seed

如果：

```text
seed
```

能够重新生成障碍物，那么即使没有直接发送 obstacles，算法仍然可以恢复隐藏信息。

所以正式 Algorithm Input 中：

```text
map_seed
```

不提供。

Seed 只允许存在于：

```text
Judge
MatchLog
Replay
```

内部。

---

# 7. Shooter 不放在 public_state

Shooter 是在人类选择阶段产生的。

因此：

```text
public_state.json
```

生成时不应该包含 Shooter。

这样它真正代表：

> 揭盲前的公开比赛世界。

---

# 8. reveal_state.json

双方 Shooter 完成 Lock 后生成。

建议：

```json
{
  "schema_version": "1.1",
  "match_id": "MATCH-001",
  "round": 4,

  "public_state_sha256": "92fa...",

  "shooters": {
    "A": "A4",
    "B": "B2"
  },

  "obstacles": [
    {
      "id": "O1",
      "type": "rectangle",
      "xmin": -1,
      "xmax": 2,
      "ymin": -5,
      "ymax": 1
    },
    {
      "id": "O2",
      "type": "circle",
      "cx": 4,
      "cy": 3,
      "radius": 2
    }
  ]
}
```

---

# 9. reveal_state 采用 Delta，而不是重复全部数据

不建议第二个 JSON 再复制一遍：

```text
points
map
alive state
```

因为这会造成两个来源可能不一致。

推荐：

```text
public_state.json
=
公开基础状态

reveal_state.json
=
隐藏信息增量
```

然后：

```text
Final Round State
=
Public State + Reveal State
```

这样职责非常清楚。

---

# 10. public_state_sha256

Reveal JSON 中加入：

```text
public_state_sha256
```

非常有价值。

例如：

```json
{
  "public_state_sha256": "92fa..."
}
```

代表：

> 这个 Reveal 文件明确绑定到这一份 Public State。

避免出现：

```text
Round 4 public state
+
Round 5 reveal state
```

这样的错误组合。

---

# 11. 两支队伍获得完全相同的两个文件

正式公平要求：

```text
SHA256(A/public_state.json)
==
SHA256(B/public_state.json)
```

同时：

```text
SHA256(A/reveal_state.json)
==
SHA256(B/reveal_state.json)
```

即：

\[
\boxed{
Public_A=Public_B
}
\]

以及：

\[
\boxed{
Reveal_A=Reveal_B
}
\]

双方看到完全一样的世界。

---

# 12. Team 身份不要通过修改 JSON 实现

不要：

### Team A

```json
{
  "my_team": "A"
}
```

### Team B

```json
{
  "my_team": "B"
}
```

这样两个 JSON 就不再完全相同。

更好的方式：

```text
Runner Slot A
Runner Slot B
```

在启动算法时通过只读 Runner Context 告诉算法自己的身份。

例如：

```bash
python solver.py \
  --team A \
  --public public_state.json \
  --reveal reveal_state.json
```

B：

```bash
python solver.py \
  --team B \
  --public public_state.json \
  --reveal reveal_state.json
```

其中两个 JSON 字节级完全相同。

唯一不同的是：

```text
--team A
```

和：

```text
--team B
```

---

# 13. 算法正式入口

V1.1 建议进一步冻结 Solver Contract。

例如：

```text
solver.py
```

正式调用：

```bash
python solver.py \
  --team A \
  --public /input/public_state.json \
  --reveal /input/reveal_state.json
```

算法读取：

```python
public_state
reveal_state
```

然后输出：

```json
{
  "dsl": {
    "...": "AST"
  }
}
```

stdout 只允许正式结果。

Debug 信息如果需要，应：

```text
stderr
```

而不是 stdout。

---

# 14. 非常重要：算法不能在 Public Stage 提前运行

这是规则核心。

错误实现：

```text
Public JSON
    ↓
launch algorithm
    ↓
algorithm precomputes for 10 seconds
    ↓
Reveal JSON arrives
    ↓
START
```

这实际上允许：

> Preprocessing。

甚至算法可以提前计算：

```text
A1 的所有方案
A2 的所有方案
A3 的所有方案
...
```

然后 Reveal 后只做选择。

这违反 V1 的公平原则。

---

# 15. 正确实现

应该是：

```text
public_state.json ready
        ↓
NO ALGORITHM PROCESS

Human selects Shooter
        ↓
reveal_state.json ready
        ↓
NO ALGORITHM PROCESS

Judge START
        ↓
create/release algorithm process
        ↓
algorithm sees both files
```

因此：

> JSON 可以提前存在，但算法执行环境不能提前执行参赛代码。

---

# 16. 为什么还要提前生成 public JSON

即使算法不会提前运行，这个文件依然有意义。

因为它：

### 1. 明确揭盲边界

可以证明：

```text
揭盲前公开了什么
```

### 2. 方便比赛审计

MatchLog 可以保存：

```text
publicStateHash
revealStateHash
```

### 3. 方便 SDK

选手可以在开发环境分别模拟：

```text
pre-reveal
reveal
```

### 4. 未来扩展

如果以后 V2 想允许：

> limited preprocessing phase

就可以在不改变数据协议的情况下增加规则。

但 V1.1：

```text
Preprocessing = OFF
```

---

# 17. Reveal 后允许停顿

Reveal 后不必立刻自动启动算法。

可以：

```text
REVEAL
```

然后展示：

```text
TEAM A SHOOTER: A4
TEAM B SHOOTER: B2

OBSTACLES REVEALED
```

现场主持人可以停留几秒。

但：

```text
算法仍未运行
```

所以停多久都不影响公平。

然后裁判：

```text
START
```

才真正进入算法竞速。

---

# 18. START 应该是一个独立的正式比赛事件

建议 UI：

```text
ROUND 5

PUBLIC STATE ✓
A SHOOTER LOCKED ✓
B SHOOTER LOCKED ✓
REVEAL STATE ✓

READY TO COMPUTE

[ START ]
```

裁判点击之后：

```text
3
2
1
GO
```

或者：

```text
START!
```

随后：

```text
TEAM A COMPUTING
TEAM B COMPUTING
```

---

# 19. START 后数据完全冻结

一旦点击：

```text
START
```

以下全部 immutable：

```text
public_state.json
reveal_state.json
shooters
points
obstacles
alive state
```

即使 A 先杀掉 B3：

B 的算法当前 Round 仍然基于：

```text
原始 public_state
+
原始 reveal_state
```

计算。

唯一例外：

如果 B 的 Shooter 在 B 开火前被杀：

```text
B SHOT CANCELLED
```

而不是重新给 B 一个新 JSON。

---

# 20. Round Hash

建议进一步计算：

```text
publicHash
revealHash
```

然后：

```text
roundHash =
SHA256(
    publicHash +
    revealHash
)
```

或者使用 Canonical Serialization 后统一计算。

正式日志记录：

```json
{
  "publicStateHash": "...",
  "revealStateHash": "...",
  "roundStateHash": "..."
}
```

这样一场争议比赛以后可以证明：

> 两支算法到底是在什么输入上进行计算的。

# 21. Round 2 的 public_state

Round 结束后：

```text
B3 dead
A5 dead
```

下一轮重新生成：

```text
public_state.json
```

例如：

```json
{
  "round": 5,
  "points": [
    {
      "id": "A5",
      "alive": false
    },
    {
      "id": "B3",
      "alive": false
    }
  ]
}
```

然后重新：

```text
Human Selection
↓
Reveal
↓
START
```

每轮完全独立。

# 22. 静态规则不要每轮塞进 JSON

例如：

```text
AST Nodes <=128
Depth <=12
Convexity <=100
Timeout=2000ms
DSL operator whitelist
```

这些不需要每 Round 重复发送。

它们属于：

```text
Competition Specification
```

在赛前通过：

```text
README / SDK / schema
```

提供。

因此算法输入分为三个逻辑层：

```text
STATIC COMPETITION SPEC
        │
        │ 开发时已知
        ▼

public_state.json
        │
        │ 每 Round
        ▼

reveal_state.json
```

最后：

```text
START
```

---

# 23. 推荐最终文件结构

每个 Runner 的只读输入：

```text
/input/
├── public_state.json
└── reveal_state.json
```

算法包：

```text
/app/
├── manifest.json
├── solver.py
└── ...
```

临时目录：

```text
/work/
```

算法只能：

```text
read /input
read /app
write /work
```

并且：

```text
/work
```

Round 结束即销毁。

---

# 24. Algorithm Output

算法只输出一次：

```json
{
  "dsl": {
    "type": "..."
  }
}
```

不允许输出：

```text
target
hit list
kills
obstacle collision
winner
```

因为这些全部由 Judge 决定。

---

# 25. V1.1 建议冻结的协议

正式定义：

```text
PRE-REVEAL
    ↓
public_state.json generated
    ↓
Human Shooter Selection
    ↓
Both Lock
    ↓
REVEAL
    ↓
reveal_state.json generated
    ↓
Judge / Host pause
    ↓
START
    ↓
Both Runner environments begin execution
    ↓
Both algorithms receive:
    public_state.json
    reveal_state.json
    team identity
    ↓
Compute
    ↓
Return DSL
```

最重要的三个原则：

\[
\boxed{\text{Public JSON 不包含隐藏信息}}
\]

\[
\boxed{\text{Reveal JSON 只补充隐藏信息}}
\]

\[
\boxed{\text{START 前参赛代码绝不运行}}
\]

# 26. V1.1 UI 与协议结合

这样 V1.1 前端也可以非常自然地对应三个状态。

## PRE-REVEAL

大屏：

```text
ROUND 5

SELECT SHOOTER
```

只显示：

```text
Points
Coordinates
Alive / Dead
```

---

## REVEAL

显示：

```text
A4 SELECTED
B2 SELECTED

OBSTACLES REVEALED
```

但：

```text
A ALGORITHM: NOT STARTED
B ALGORITHM: NOT STARTED
```

---

## START

裁判：

```text
[ START COMPUTATION ]
```

点击：

```text
GO
```

大屏：

```text
TEAM A COMPUTING...

TEAM B COMPUTING...
```

从这里才开始出现算法计时。

# 27. V1.1 对观众特别有价值

这个结构会让观众非常容易理解比赛：

```text
第一步：
人选点

第二步：
地图揭盲

第三步：
裁判发令

第四步：
算法赛跑

第五步：
函数攻击
```

这比：

> 点一下之后突然发生一堆后台计算

有明显更好的现场感。

# 28. V1.1 实现时的 Compatibility 原则

V1.0 已经冻结：

```text
v1.0.0-competition
```

因此 V1.1 实现这个协议时：

- 不修改 V1.0 tag；
- 从新 branch 开发；
- 尽量保持现有 Judge / Sandbox 逻辑；
- 两阶段 JSON 属于输入协议与 orchestration 改进；
- 任何涉及核心公平性的改动必须有 regression。

建议：

```text
feature/v1.1-ui-protocol
```

或：

```text
feature/v1.1-platform-polish
```

作为新开发分支。
