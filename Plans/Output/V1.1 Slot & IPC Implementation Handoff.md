## 2. 逐节实现对照

### §2–§4 固定槽位与固定入口

- 新增 `src/submission/Slot.ts`：槽位模型、状态读取（`EMPTY` / `READY` / `INVALID`）、
  staging / commit / discard、安装记录读写。
- `algorithms/team-a/solver.py`、`algorithms/team-b/solver.py` 出厂为 starter 副本，
  两槽位结构完全一致（`algorithm-slot` 逐文件清单断言）。
- `Manifest.ts`：`ENTRY_FILENAME = 'solver.py'`；`manifest.entry` 变为可选，
  写了就必须是 `solver.py`，否则**明确拒绝**（硬切，不静默忽略）。
- `Package.ts`：`manifest.json` 变为可选元数据；缺 `manifest.json` 不再算错误，
  缺**包根目录的** `solver.py` 才算错误。

### §5 固定 Runtime

- 新增 `src/submission/Runtime.ts`：`FROZEN_RUNTIME`（CPython 3.9.6 / numpy 2.0.2 /
  scipy 1.13.1 / sympy 禁用 / 1 核 / 512 MB / 1 线程 / 2000 ms）+ `detectRuntime()`
  + `checkRuntime()`。
- `startMatch()` 写入 `RuntimeFrozen` 审计事件（冻结清单 + 宿主实测 + 差异），
  差异**不阻断**比赛，但留痕。
- `scrubEnv` 注入 `THREAD_ENV`（`OMP_/OPENBLAS_/MKL_/NUMEXPR_/VECLIB_` 线程数全为 1），
  `process-tree-cleanup` 逐条断言。

### §6–§12 固定启动命令与四区沙箱

- argv 固定为 `--team / --public / --reveal / --output`（顺序固定），双方唯一差异是 `--team` 的取值。
- 沙箱四区：`app/`（只读包）、`input/`（只读两份 JSON，0444）、`output/`（只写）、`work/`（唯一可写）。

### §13–§17 输入文件

- 沿用第一份 V1.1 规范的 `InputProtocol`：public 不含障碍物 / 种子 / Shooter；
  reveal 是 delta 且带 `public_state_sha256` 绑定；两份文件对 A/B **逐字节相同**。

### §18–§23 启动与计时

- bootstrap 在收到 GO 之前不执行参赛代码（`pre-start-execution` 用模块顶层探针硬断言，
  并配正向对照防假阳性）。
- 计时锚点：结果文件**自身写成的时刻**（`mtime`，纳秒）− **本队自己的** GO 写入时刻（`releaseNs`）。
  两侧各自独立起算，`startSkewNs` 只作审计量、不参与计时。
- 释放前双方都先 `prepare()`（挂好轮询器与超时预算），`release()` 只剩「打点 + 写 GO」，
  使两次 GO 写入之间的宿主开销降到最低 —— 该开销方向固定，会整体计入**先写方**的耗时。

### §24–§30 输出与 deadline

- 结果只经 `output/result.json`；stdout 不是 IPC（`result-ipc` 用「stdout 与文件写不同 DSL」
  的探针证明判定只取文件）。
- `parseResultFile()` 严格校验：顶层必须是对象、只允许 `schema_version` 与 `dsl`、
  `schema_version` 必须精确为 `"1.1"`、`dsl` 必须存在。
- 1 ms 轮询监听文件出现；结果到达后给 50 ms 排空 stderr 再强杀（ONE OUTPUT ONLY）。
  轮询回调只负责**发现**结果，耗时结算用文件自身的 `mtime`（见 §18–§23）：
  宿主回调是串行的，先返回的一方会推迟后一方的读数。
- 进程可能在写完结果的同一拍退出（1 ms 轮询还没轮到它）：`close` 处理器在收尾前
  补做一次同步检查，否则合规算法（tmp + 原子 rename 后立即结束）会被误判 `INVALID_OUTPUT`。
- 错误码分界：**进程退出时**留下完整但非法的结果 → `INVALID_OUTPUT`（§29）；
  deadline 前从未出现完整合法结果（含写半截卡住） → `TIMEOUT`（§28）。

### §31–§33 上传与槽位 UI

- `MatchEngine.installAlgorithm()` 编排 `staging → validate → preflight → hash → seal → replace`，
  任何一步失败都丢弃暂存副本、**不动现有槽位**，并记 `SlotRejected`（带 `stage`）。
- preflight 用 decoy 世界，对手固定为平台 `starter`（验证一队不依赖另一队槽位状态）。
- 槽位元数据写在 `<slotRoot>/.slots/<team>.json`：它不属于算法包，
  不进包哈希、不进沙箱（`algorithm-slot` 断言）。
- `MatchSetupUI.renderSlotPanel()` 实现 §33 的面板（Status / Entrypoint / Hash / Preflight / REPLACE）。

### §34–§35 Preflight 与正式运行分开

- decoy 种子由 `matchId` 派生，与操作员 `--seed` 无关；撞车自动换种（`preflight-decoy`）。

### §39 SDK 模板

- `starter/solver.py` 重写为 4 参数模板：`load_input()`（含绑定自检）+ `emit()`（tmp + fsync + 原子 rename）。

### §41 文件结构

- 新增 `algorithms/`（含 `README.md`）、`algorithms/.staging/` 与 `algorithms/.slots/`（gitignore）。

## 4. 已知偏差与决策记录

1. **`--max-rounds`（操作台护栏，默认 50）** —— 规范未定义僵局规则，
   而 `getWinner()` 在双方都打不中时永远返回 `null`（出厂 starter 与它对局即会僵持）。
   引擎判定语义保持不变，由操作台在达到上限时停止并报告 `UNDECIDED`，产物照常落盘。
2. **`--a/--b` 默认安装进仓库内的 `algorithms/`** —— 这是 §31/§32 的正式流程，
   因此一次真实上传会让工作区出现改动。测试一律显式传 `--slots`，绝不改写工作区。
3. **`INVALID_OUTPUT` 与 `TIMEOUT` 的分界** —— 见 §2 的 §24–§30 小节；
   两者都必须可区分，否则现场无法判断「算法写错了」还是「根本没写出来」。
4. **`manifest.entry` 硬切** —— 不再读取，但写错会明确报错，而不是静默忽略。
5. **计时终点改用结果文件 `mtime`（本实现期发现并修正的偏置）** —— V1.1 的结果通道从
   stdin 改为文件后，`timing-fairness` 出现回归（同算法 300 轮「A 更快」比例 0.873，
   断言未改）。根因不在算法，而在宿主：1 ms 轮询回调里先 `existsSync` + `readFileSync` +
   解析，**再**打时间戳，于是 A 的回调把 B 的打点推迟约 100µs，方向固定。
   改用文件时间戳后仍不对称，遂做了一组对照实验（两个真实 Python 进程，释放间隔 27µs）：
   宿主 GO 写入偏差中位 85µs，但**算法实际收到 GO 的时刻偏差中位 0.0µs**，
   完成写入偏差中位 −0.1µs —— 即真实的计算窗口是对称的，偏置完全来自宿主的打点。
   结论：终点取 `mtime`（写入时刻，随 rename 保留），并让沙箱拒绝 `utimes` 使其不可伪造；
   `ctime` 不可用（rename 更新它，且 fsync/事务屏障会把完成时刻同步化，反而放大释放偏差）。
   还剩一个同向偏置：两次 GO 写入之间的宿主开销整体计入**先写方**的耗时。做了三项收窄 ——
   ① 释放前双方先 `prepare()`（轮询器与超时预算提前挂好），`release()` 只剩打点 + 写；
   ② `stdin.end()` 推迟到下一拍（交错配对实测它给后写方多加约 16µs）；
   ③ `prepare()` 里用一次 0 字节写预热 stdin 的写入路径 —— 本轮**第一次** `write()`
   比后续写贵约 35µs（探针实测 39.5µs → 5.4µs，属 JS 侧惰性初始化），而 GO 正是第一次写。
   三项合计把 `startSkewUs` 中位数从 25.6µs 压到 5.4µs，同算法「A 更快」比例从 0.405
   回到 0.467（阈值 0.4–0.6）。5.4µs 比引擎的先手判定阈值 `TIE_EPS_MS = 0.05`（50µs）
   小一个数量级，即残差已落在「判为先手平局」的区间内。
   `timing-fairness` 的断言**一条未改**。
6. **沙箱写权限收窄** —— 从 `(allow file-write*)` 收窄为 `file-write-data` /
   `file-write-create` / `file-write-unlink` 三条，`file-write-times`（`utimes`）被拒。
   用独立 SBPL 配置实测：tmp + fsync + 原子 rename、覆盖写、建子目录、写 `__pycache__`
   均可用，`os.utime` 抛 `PermissionError [Errno 1]`。这是上一条的前提 ——
   `mtime` 若可被参赛代码回拨，计时就能被伪造。
