## 3. Revision 3 的规则要点（交接时必须一起交出去的部分）

```text
固定 Emitter      A @ (-18, 0) / B @ (18, 0)，整场不变、不可更换、不可击杀
                  它不是战斗点：不计入 alive、不能作为胜利目标
函数锚点          |f(x_e) − y_e| ≤ 1e-6，x_e / y_e 是常量
流程              PUBLIC → REVEAL → START → COMPUTE → RESOLVE
                  每轮不再有人工选点 / SHOOTER LOCK / Shooter reveal
输入              public_state.json 含 emitters；reveal_state.json 只含 obstacles
终止（穷举）      ELIMINATION → 幸存方胜
                  MUTUAL_ELIMINATION → DRAW
                  STALEMATE（连续 20 回合零击杀）→ DRAW
                  HARD_ROUND_LIMIT（第 60 回合）→ DRAW
预算              500 ms（从 GO 起算）
```

**终止保证落在 `MatchEngine` 里**，不是 CLI 参数 —— 任何调用方（包括未来的 UI）
都不可能跑出一场不终止的比赛。

## 6. 本轮修复的一个真缺陷（必须让审计方知道）

Revision 3 的**第一次** 180 场 playtest 跑完时，**180 场全部被记成 `draw`**。

根因：`MatchEngine.getMatchLog()` / `getReplay()` 的 `winner` 写成
`this.terminalReason ? 'draw' : this.getWinner() ?? 'draw'` —— `terminalReason`
在**任何**终局都会设置，于是「一方全灭」也被强制写成平局。
`RoundResult.winner`（内存返回值）是对的，错的只有落盘日志与回放，
所以**既有套件全部通过**：没有一条用例断言过「ELIMINATION 时日志里的 winner 是谁」。

已修复 + 已补逐终局分支的回归；第一次 playtest 的归档整体删除并重跑。

> 这条值得审计方单独看一眼：它说明「四类终局」这类**新代码路径**必须逐分支断言，
> 否则成套的回归会出现「全绿但全错」的情况。
