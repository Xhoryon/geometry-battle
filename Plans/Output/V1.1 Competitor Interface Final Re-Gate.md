### IMPORTANT-1：文档承诺的「多文件算法包」不成立

`ALGORITHM_REQUIREMENTS.md` §1 明确写：

```text
my-algorithm/
├── solver.py
├── optimizer.py       ← 可选：你自己的其它模块
└── utils/             ← 可选：你自己的子目录
```

我按这段话**原样**写了一个多文件包（`solver.py` + `strategy.py` + `utils/helper.py`，
用最自然的 `import strategy` / `from utils import helper`），跑官方 Local Validator：

```
CLI / startup      PASS READY 握手成功
Result JSON        FAIL 算法未产出合法的 output/result.json（errorCode=CRASH）
    ↳ 算法异常退出 (code=1): Traceback (most recent call last):
      ModuleNotFoundError: No module named 'strategy'
PRE-FLIGHT FAIL — 失败分节: A/Result JSON, B/Result JSON
```

根因（我在真实沙箱里用 `/tmp/audit-probe2` 独立证实）：
生产启动壳 `BOOTSTRAP_SOURCE` 用 `runpy.run_path(entry, run_name='__main__')` 启动入口，
`runpy.run_path` 对**脚本文件**不修改 `sys.path`，而 `sys.path[0]` 是沙箱目录
（`__gb_bootstrap.py` 所在处），**不是** `app/`。实测：

```
sys_path: ["<sandbox>", ".../python39.zip", ".../python3.9", ".../lib-dynload", ".../site-packages"]
import_helper   -> ModuleNotFoundError: No module named 'helper'
import_utils_mod-> ModuleNotFoundError: No module named 'utils'
```

**规避手段（通用 Python 写法，不需要读生产源码）**：在 `solver.py` 顶部加
`sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))`。我实测同样的包
加这一行后：

```
PRE-FLIGHT PASS — 2 个队别 × 9 个分节全部通过
```

判定：**不是 BLOCKER**（单文件包 first-try 通过；错误信息可读；修复是标准写法），
但**文档高估了平台能力**，与 `ALGORITHM_REQUIREMENTS.md` §1 的措辞冲突。
要么让启动壳把 `app/` 加入 `sys.path`，要么在文档里写明「多文件包需要自行把包目录
加入 `sys.path`」。注意 `tests/competitor-kit.ts` **没有**覆盖多文件包，所以这个
偏差不会被现有回归发现。

## Timing Evidence

**我独立复现，未修改任何阈值，未与其他重负载并发。**
命令：`node -r ts-node/register tests/timing-fairness.ts`（独立运行，连跑 3 次）。

| 我的第 N 次运行 | aFasterRate | medianTimeA / B | timeDiff median / p95 | startSkew 中位 / p95 | swap Δ | 结果 |
|---|---|---|---|---|---|---|
| 第 1 次 | **0.367** | 21.64 / 21.42 ms | 0.007 / 0.604 ms | 5.167 / 7.625 µs | 0.013 | **✗ 套件 FAIL** |

| 第 3 次 | 0.470 | 19.46 / 19.52 ms | 0.005 / 0.547 ms | 5.209 / 6.833 µs | 0.013 | ✓ 3/3 |

加上开发方 Handoff §4.1 自己记录的四次（`0.400`✗ / `0.430` / `0.403` / `0.450`），
**累计 7 次观测，aFasterRate 全部 < 0.5**（0.367、0.400、0.403、0.420、0.430、0.450、0.470，
均值 ≈ 0.42）。也就是说：

- **方向稳定**：`aFaster` = 「A 的 computeTime 更小」，恒 < 0.5 意味着
  **B 在多数轮次里被记为更快**，进而按 `src/core/Match.ts` 的 `firstSolver` 逻辑
  拿到先手（`TIE_EPS_MS = 0.05`，只有 `|tA−tB| ≤ 0.05ms` 才算 tie）。
- **量级很小**：`median(diffs)` ≈ 0.005–0.007 ms（约 0.03% 的 2000 ms 预算），
  p95 约 0.4–0.6 ms。
- **可定位的根因**：`runDuel()` **永远先 release A、再 release B**
  （`releaseANs = runnerA.release(); releaseBNs = runnerB.release();`），
  实测 `startSkew` 中位数 ≈ 5.2 µs。由于「每方从**自己**的 GO 起算」，
  A 的基准永远早 ~5 µs，在双方绝对完成时刻相同时，A 的 `computeTimeMs`
  就恒比 B 大 ~5 µs —— **方向固定的偏置**，其量级恰好等于 startSkew
  （实测 timeDiff 中位数 0.005–0.007 ms ≈ startSkew 5.2 µs）。这修正了 V1.0
  的共享时间戳问题，但没有消除方向性：只是把偏置从 ~20 µs 降到 ~5 µs。
- **对局面的影响**：`swapBatch`（换序胜率）稳定给出 Δ=0.013（1.3 个百分点），
  远低于其 0.15 的断言阈值，且三次完全一致 —— 说明对**胜负结果**的影响很小；
  但对「谁先结算」的影响约 8 个百分点（50% → ~58% B 先手）。

判定：按本轮审计指令「若存在稳定方向性优势，必须升级为 blocker」——
**存在稳定方向性优势，升级为 BLOCKER（B-1）**。同时如实记录：量级小、swap Δ 小、
单次 0.367 距离 0.4 阈值并不算「恰好落在边缘」（低于阈值 3.3 个百分点，
300 轮的标准误约 2.9 个百分点）。永久套件因此**间歇性变红**（我的 3 次里红 1 次，
开发方 5 次里红 1 次，合计约 2/8）。

## Remaining Findings

### BLOCKER

**B-1 计时公平性存在方向固定的偏置（偏向 B）**
- 证据：见「Timing Evidence」。7/7 次观测 aFasterRate < 0.5；永久套件在
  我第 1 次运行即失败（0.367 < 0.4）。
- 根因：`runDuel()` 固定先释放 A；每方以自己 GO 起算 → A 恒被多计一个 `startSkew`（≈5 µs）。
- 影响：B 拿到「先结算」的概率约 58%（对局结果层面 Δ≈1.3pp）。
- 建议方向（**我没有改任何代码**）：让两次 GO 的写入真正对称（例如同时打点后再写，
  或把双方的计时基准都取 `min(releaseA, releaseB)` 并把该偏差如实扣除），
  或在文档与审计中显式承认该偏置并给出可接受的量级。
- 注意：**不得**通过放宽 `0.4 < aFasterRate < 0.6` 阈值来「修复」。

### IMPORTANT

**I-1 公开文档承诺的「自带 `.py` 模块 / `utils/` 子目录」在正式沙箱内不成立**
- 证据：见「Fresh Competitor Test / IMPORTANT-1」。按 §1 原样写多文件包 →
  `ModuleNotFoundError`，Preflight FAIL。加 `sys.path.insert(0, 包目录)` 后 PASS。
- 影响：陌生参赛者若按文档组织多文件包，首次提交必失败一轮；错误信息可读，修复是标准写法。
- 现有回归 `tests/competitor-kit.ts` 未覆盖多文件包，因此该偏差不会被自动发现。

### MINOR

- **M-1** `RUNTIME_MANIFEST.md` §6「沙箱内只保留以下变量（其余一律清空）」不精确：
  实测 22 个变量，另有 7 个由 macOS/launcher 注入的良性变量（`CPATH`、`LIBRARY_PATH`、
  `MANPATH`、`PWD`、`SDKROOT`、`SHLVL`、`__CF_USER_TEXT_ENCODING`），**不含宿主敏感变量**。
- **M-2** `competitor-kit/starter/solver.py` 顶部注释引用

  这是仓库内部路径，不在 `competitor-kit/` 内，单独拿到 kit 的参赛者无法解析。
  （`ALGORITHM_REQUIREMENTS.md` §0 声称「文中提到的每一个文件…都真实存在于
  competitor-kit/」，这条引用是反例；不影响任何判定。）
- **M-3** Local Validator 是「Python 前端 + 仓库内 `src/operator/validate-submission.ts`」，
  因此**必须**在完整仓库内运行；只拿到 `competitor-kit/` 目录无法自检。
