## 2. Revision 3 final rules

### 2.1 固定 Emitter（§2–§7）

```text
Team A:  Emitter A0 @ (-18, 0)      战斗点 A1..An
Team B:  Emitter B0 @ ( 18, 0)      战斗点 B1..Bn
```

Emitter 在整个 Match 中：**固定、不可更换、不可死亡、不可被击杀、不可被消除**，
是「永久函数发射锚点」。它：

- **不是战斗点** —— 不计入 `alive`、不能作为胜利目标、不参与击杀；
- **公开** —— 从第 1 轮的 `public_state.emitters` 起就可见；
- **不可击杀** —— 轨迹穿过它不产生任何效果；「Shooter assassination」概念已删除。

**实现上的关键选择**：Emitter **不在 `points` 数组里**，而是独立字段。
这样 `getWinner()` / `aliveAfter` / 敌人筛选 / `markDead()` / 回放绘制这些
「遍历 Points」的路径**一行都不用改**，也就不存在「某一处忘了排除」的漏判空间。

### 2.2 函数锚点（§4）

每轮函数必须经过本队的固定 Emitter：

```text
|f(x_e) − y_e| ≤ 1e-6        x_e / y_e 是常量
```

### 2.3 删除 Shooter Selection（§5）

正式流程不再有：每轮人工选点、`SHOOTER LOCK`、Shooter reveal、Shooter replacement。

```text
PUBLIC → REVEAL → START → COMPUTE → RESOLVE
```

REVEAL 仍然存在（障碍物是隐藏信息），但**只剩障碍物** ——
`reveal_state.json` 里的 `shooters` 字段已删除，发射锚点改在 public 里给出。

**状态机 19 → 16 阶段**：`SHOOTER_SELECTION` → `PUBLIC`；
删除 `A_LOCKED` / `B_LOCKED` / `CHECK_SHOOTER`（Emitter 不会死，无「检查存活」可言）。

### 2.4 胜负与终止（§8–§10/§16/§17）

胜负**只看战斗点**。四类终止方式**穷举**全部情形：

| `endReason` | 触发 | 结果 |
|---|---|---|
| `ELIMINATION` | 一方战斗点归零、另一方仍有 | 幸存方获胜 |
| `MUTUAL_ELIMINATION` | 同一轮结束后双方同时归零 | **DRAW** |
| `STALEMATE` | 连续 **20** 回合双方合计击杀为 0 | **DRAW** |
| `HARD_ROUND_LIMIT` | 到达第 **60** 回合 | **DRAW** |

**终止保证由引擎自身实现**：不再依赖 CLI 的 `--max-rounds`（它已降级为纯兜底）。
这是 §17 要求的「Every valid Geometry Battle match terminates in finite time」的落地方式 ——
把保证放进 `MatchEngine`，而不是放进调用方的参数。

`MUTUAL_ELIMINATION` 是 Revision 2 遗留的正确部分：先手清零对方之后，后手凭
**已锁定的攻击权**可以反过来清零先手方。**不得**因为谁是 First Solver 就判谁赢。

## 3. 500 ms timing decision

§11 要求用数据决定，并给出了明确的判据：若 500ms 对正常参考算法产生明显非预期 TIMEOUT，
可以报告 `750ms recommended`；否则保持 500ms。

**方法**：同一批 3 个 map condition × 2 种 A/B 摆位 × 3 个配对，
在 250 / 500 / 750 ms 下各跑一遍，统计每个「队伍×回合」的 `TIMEOUT`。
三个参考算法**未做任何策略适配**（只把锚点读取从 `reveal.shooters` 改成
`public.emitters`，见 §7）。

| 预算 | 样本（队伍×回合） | TIMEOUT | TIMEOUT 率 | 整场失败 |
|---|---|---|---|---|
| 250 ms | 128 | 20（**全部是 optimizer**） | **15.6%** | 7 场 |
| 500 ms | 218 | **0** | **0%** | 0 |
| 750 ms | 218 | **0** | **0%** | 0 |

**决定：保持 500 ms**（不回升到 2000 ms）。理由：500ms 下三个参考算法在 218 个
样本上一次超时都没有，同时预算被收紧到原来的四分之一 —— 符合 §11 的目标
（支持现有合法算法、改善 pacing、防止超长优化搜索）。
250ms 则已经**实质性地破坏**参考优化器（它在 decoy preflight 里就超时，让整场失败）。

**已知局限（如实记录）**：这项 benchmark 只用了 3 个 map condition，
500ms 的 0 超时结论有较大的置信区间。§9 的 180 场最终 playtest 使用默认 500ms，
给出了更大样本的补充证据。

## 4. Stalemate decision

**阈值来自数据，不是拍脑袋。**

Revision 2 的测量已经确立了一件事：**僵持不是「回合数不够」，而是吸收式不动点**。
把上限从 30 抬到 60，触顶的对局**几乎全部仍未化解**（fast-vs-hybrid 的 32 场里
22 场仍在 60 轮触顶）。因此阈值只需要覆盖「局面已经冻结之后不久」，不需要留大余量。

**冻结值**：

```text
NO-PROGRESS LIMIT = 20 连续回合（双方合计击杀 = 0）
HARD ROUND LIMIT  = 60 回合
```

两者都判 **MATCH DRAW**（§16 要求「优先 MATCH DRAW；除非规则证据强烈支持一个简单、
无争议的 tiebreak」）。本轮**没有**发明任何隐藏评分或 tiebreak。

`NoProgressStreak` 逐轮写入 `RoundLog` 并可事后复核：
判据不看谁先手、不看函数是否合法 —— 双方都交出合法解但谁也打不中，同样是僵持。

## 7. 关于参考算法的一个必须说清的边界

任务书 §12 要求：**不要修改 `solver-fast` / `solver-optimizer` / `solver-hybrid`**，
因为这一轮要测的是 `RULE EFFECT` 而不是 `ADAPTED META`。

但 Revision 3 改了**输入契约**：锚点从 `reveal.shooters`（一个 id）搬到
`public.emitters`（直接给坐标）。不改这一步，算法根本读不到锚点、连 Preflight 都过不了。

**因此本轮对三个参考算法只做了一处改动**：

```python
me = by_id[shooters[team]]            # 旧：从 public.points 里按 id 反查
me = (public.get("emitters") or {}).get(team)   # 新：直接取公开的常量坐标
```

策略、搜索、打分、预算、早返回逻辑**一行未改**。
`reveal.get("shooters")` 仍按旧字段读 —— 在新输入下恒为空，于是
`enemy_shooter_id` 恒为 `None`，即「刺杀敌方 Shooter」的加成分支**自然失效**
（Revision 3 下 Emitter 不可击杀、也不在 `points` 里，本来就无此目标）。

**副作用（必须计入解读）**：参考算法内部的时间预算（optimizer 约 1500ms）没有跟随
规则改成 500ms。它们在 500ms 内的超时率见 §3 —— 实测为 0，但这是**测量结果**，
不是设计保证。为 Revision 3 重新调优算法属于下一轮 `ADAPTED META` 实验。

## 9. Final playtest

**规模**：与 round-1 / round-2 相同的 **30 个 map condition** × 2 种 A/B 摆位 × 3 配对
= **180 场**，使用 Revision 3 的生产规则与默认 500ms 预算。

**产物**：`playtest/results/revision-3/`（逐场 `console.log` / `match.json` /
`replay.json` / `audit.json` / `summary.json` + `metrics-*.json` + 汇总）。

**0 INVALID · 0 CRASH**，TIMEOUT 共 2 次（均在 fast-vs-hybrid）；`shotCancellationRate` 全为 **0.0**。

| 配对 | 胜场 | DRAW | 合计 |

| fast-vs-optimizer | fast **14** · optimizer **25** | 21 | 60 |

### 终止方式的分布

| 配对 | ELIMINATION | MUTUAL_ELIMINATION | STALEMATE | HARD_ROUND_LIMIT |
|---|---|---|---|---|
| fast-vs-hybrid | 37 | 6 | 17 | 0 |

`HARD_ROUND_LIMIT = 0` 是**预期结果**：Stalemate 在连续 20 个零击杀回合后先触发，而 180 场里最长的一局只有 **28 回合**，离 60 的硬上限还很远。硬上限是**兜底**而非常用路径 —— 但终止保证仍然成立（四类穷举）。

### 匹配时长与僵持

| 指标 | 值 |
|---|---|
| 回合数 median / mean / p95 / max | 5.0 / 10.094 / 26.0 / **28** |
| 连续零击杀 median / p75 / p95 / max | 0.0 / 20.0 / 20.0 / **20** |
| 打满上限的对局 | 0 / 180 |

`noProgressStreak` 的 max 恰好等于阈值 **20** —— 阈值是**生效的边界**，不是「数据恰好没触到」。同时也说明僵持确实存在：180 场里有 **51 场（28.3%）**由 Stalemate 规则收场。

### 每个算法的表现

| 算法 | 回合数 | 先手率 | 每有效射击击杀 | 多杀率 | 无命中率 | TIMEOUT |
|---|---|---|---|---|---|---|
| fast | 1185 | 0.879 | 0.6807 | 0.212 | 0.542 | 1 |
| hybrid | 1260 | 0.586 | 0.5894 | 0.186 | 0.689 | 1 |
| optimizer | 1189 | 0.026 | 0.7258 | 0.290 | 0.632 | 0 |

**速度仍然拿先手，但不再转化为支配**：fast 先手率 0.879（optimizer 0.026），而 fast 在 180 场里拿到 **32 胜**、其中 **14 场**直接赢下与 optimizer 的对局。

### 9.2 与历史轮次的对照

### 9.2 与历史轮次的对照

| 配对 | Rev 1（取消规则） | Rev 2（锁定攻击权 + 每轮选点） | **Rev 3（固定 Emitter）** |
|---|---|---|---|
| fast-vs-hybrid | 26-8-26 | 13-10-37 | **18-19-23** |
| optimizer-vs-hybrid | 39-4-17（hybrid 胜） | 3-37-20（optimizer 胜） | **21-9-30** |
| fast-vs-optimizer | 50-0-10（fast 胜） | 2-38-20（optimizer 胜） | **14-25-21** |

**判读**：

- Rev 1 的坍缩（`50-0`）来自「先手击杀对方 Shooter ⇒ 取消对方攻击」这条**人为通道**；
- Rev 2 关掉了那条通道，但「每轮从存活点里选一个 Shooter」让**函数质量**成为唯一通道，坍缩换了方向（`38-2` / `37-3`）；
- **Rev 3 把锚点固定成常量**：双方每一轮从**同一个点**出发。速度只决定结算顺序，不再决定谁能开火；函数质量也不再被「先手方这一轮从哪个点打」放大。三对配对全部回到竞争区间。

### 9.3 一个必须单独说明的缺陷（本轮引入、本轮修复）

Revision 3 的**第一次** 180 场 playtest 跑完后，**180 场全部被记成 `draw`** ——
三对配对的 `wins` 全是 0。

**根因**：`MatchEngine.getMatchLog()` / `getReplay()` 的 `winner` 字段写成
`this.terminalReason ? 'draw' : this.getWinner() ?? 'draw'`。
`terminalReason` 在**任何**终局（含 `ELIMINATION`）都会被设置，于是这个三元表达式
把「一方全灭」的比赛也强制写成 `draw`。逐场核对确认：
`s1010-p8-medium__hybrid-A` 的 `endReason = ELIMINATION`、`finalAlive = {A:0, B:3}`，
而 `winner` 却写着 `draw`。

**为什么此前全套件全绿**：`RoundResult.winner`（内存返回值）是对的，
错的只有**落盘的日志与回放**；而且**没有任何一条既有用例断言过
「ELIMINATION 时日志里的 winner 是谁」**。

**处理**：
1. 修复为 `winner: this.getWinner() ?? 'draw'`（规范 §43：胜负只看存活战况）；
2. 新增逐终局分支的回归（`tests/full-match-e2e.ts`）；
3. 第一次 playtest 的归档是**有缺陷引擎的输出**，整体删除并重跑 ——
   本报告 §9.1 的数据全部来自修复后的重跑。

完整过程见 `docs/development_log.md` 阶段 6。
