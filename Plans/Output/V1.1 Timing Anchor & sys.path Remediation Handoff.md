## 2. B-1：根因与修法

### 2.1 先分清两种互斥的微观解释

审计给出的根因是「`runDuel()` 永远先 release A → A 的基准更早 ~5µs」，
但这句话对应两种**完全不同**的修法，必须先判定哪一种为真：

| 假设 | 含义 | 正确的修法 |
|---|---|---|
| **H1** | 交付是对称的，是**宿主打点**偏早 | 共用锚点 / 锚点后移 |
| **H2** | 交付本身就不对称，宿主打点如实 | 保持各自锚点，把**顺序**对称化 |

### 2.2 微探针（独立于生产代码）

用两个阻塞在 `os.read(0, …)` 的 Python 子进程 + Node 宿主复刻「打点 → 写 GO」，
测量三件事（每次 200 样本，中位数）：

| 量 | 第 1 次 | 第 2 次 |
|---|---|---|
| 宿主打点差 `tB0 − tA0` | **10.04 µs** | **10.79 µs** |
| 两次 `write()` 调用自身耗时 A / B | — | **10.67 / 3.00 µs** |
| 子进程观测的 GO 到达差 `cb − ca` | **4.25 µs** | **9.00 µs** |
| 超出部分（打点差 − 交付差） | **5.79 µs** | **1.79 µs** |

结论：**交付确实不对称（4–9µs），但宿主打点比交付还要早 2–6µs** ——
多出来的这一段正是**先释放方那一次 `write()` 调用的自身耗时**。
由于 `write('GO')` 内部才把字节交给内核，把打点放在调用**之前**，
就等于声称「A 在它自己的写入开始前就起跑了」。

**量级自洽**：一次写入调用约 3–11µs，与实测的多余偏置 2–6µs、以及生产路径上
逐轮耗时差中位 0.005–0.007ms 是同一个数量级。

### 2.3 修法

```ts
// 前：先打点、再写 GO —— 这次写入的耗时被记成本队的计算耗时
releaseNs = process.hrtime.bigint();
proc.stdin?.write('GO\n');

// 后：先写 GO、再打点 —— 锚点即交付时刻
proc.stdin?.write('GO\n');
releaseNs = process.hrtime.bigint();
```

**为什么不做另外几种**：

- **共用同一个锚点**（把双方的基准都取某个共同时刻）：会把交付差 4–9µs 重新塞回去，
  正是 Cycle 1 已经修掉的 P1-B 问题，只是方向反过来。
- **取 `min(releaseA, releaseB)` 再扣偏差**：等价于现状或反向偏置，且解释成本高。
- **逐轮交替释放顺序**：确实能把方向偏置在**期望**上抹平，但它同时会让永久套件
  **失去探测能力**（任何残余偏置都被交替抵消，0.4/0.6 断言再也抓不到）
  —— 而 0.4/0.6 恰恰是本轮唯一能分辨微秒级偏置的仪器，不能把它弄瞎。
- **改 `TIE_EPS_MS` / 放宽 `0.4 < aFasterRate < 0.6`**：明令禁止，且治标不治本。

### 2.4 残余与实际影响（如实记录）

- 修复后 4 次观测为 **0.477 / 0.477 / 0.463 / 0.440**（均值 **0.464**）。
  300 轮下单次标准误约 **2.9 个百分点**。
- 与修复前的对比要**如实说清**：修复前 7 次均值 0.42（0.367–0.470），修复后 4 次均值 0.464（0.440–0.477）。
  均值上移约 **+4.4pp**，两组均值差的合并标准误约 1.8pp，即约 **2.4σ** ——
  **一致于「机制为真且已被部分修正」，但达不到「已彻底消除」的强度**。
  两组观测区间仍然重叠（修复前的 0.470 与修复后的 0.440）。
- 因此**不宣称「无偏」**。能宣的是：**修复前那个稳定、单向的偏置已被显著削弱，
  且修复后 4/4 次都通过了 0.4/0.6 的冻结断言**（修复前 7/7 次全部低于 0.5）。
  残余量级无法从现有样本分离出来（≲4pp 与 0 在 4 个样本下不可区分）。
- 残余对**实际胜负**的影响仍被 50µs 死区压制，见下条。
- 残余来源有物理上的合理解释：先释放的一方虽然更早起跑，但起跑时宿主仍在写另一方的 GO，
  它的前几微秒要与其他工作争用，**实际计算耗时略长**。
- **对局面的实际影响远小于「8 个百分点」**：`firstSolver` 的判定
  （`src/core/Match.ts:823`）带 `TIE_EPS_MS = 0.05`（**50µs**）的死区 ——
  `|tA − tB| ≤ 50µs` 记 tie。而实测逐轮耗时差的**中位数只有 2–5µs**，
  即多数回合本来就落在死区内。一个 2µs 量级的锚点差异要改变先手，
  需要该轮差值恰好落在 ±50µs 边界的两微秒之内，其概率远低于一个百分点。
  （审计报告的「约 8 个百分点」是对 `aFasterRate` 的直读，
  该指标**不经过** `TIE_EPS_MS` 死区，因此高估了它对 `firstSolver` 的影响。）

## 3. I-1：根因与修法

`runpy.run_path(entry, run_name='__main__')` 对**脚本文件**不修改 `sys.path`
（`sys.path[0]` 是启动壳 `__gb_bootstrap.py` 所在的沙箱目录，不是 `app/`），
因此包内 `import strategy` / `from utils import helper` 一律 `ModuleNotFoundError`。

修法：在 `runpy` 之前，把入口文件所在目录（即算法包根目录）插入 `sys.path` ——
这正是 `python solver.py` 的默认行为。加在 **GO 之后、`runpy` 之前**，
因此不违反「START 前绝不执行参赛代码」：插入路径不是执行参赛代码。

```python
pkg_root = os.path.dirname(os.path.abspath(entry))
if pkg_root not in sys.path:
    sys.path.insert(0, pkg_root)
```

**永久回归**（`tests/competitor-kit.ts`）：按 `ALGORITHM_REQUIREMENTS.md` §1 的措辞
**原样**写出 `solver.py` + `strategy.py` + `utils/helper.py` 三个文件，
**不自行修改 `sys.path`**，直接过 `validateSubmission()`（与官方 Preflight 同一份判定代码）。
修复前必然 `CRASH / ModuleNotFoundError`。
