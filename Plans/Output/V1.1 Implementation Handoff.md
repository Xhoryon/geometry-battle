## 1. 结论

V1.1 的两阶段输入协议、START 门禁、三段式编排、沙箱三区与 decoy preflight 已全部落地，
新增 4 个回归套件（共 24 个用例），原有 18 个套件的**判定语义断言一条未改**。

本协议解决的是 V1.0 的四处实质缺陷：

| # | V1.0 缺陷 | V1.1 处置 | 回归 |
|---|---|---|---|
| 1 | 单一 stdin 载荷把 `map_seed` / `obstacles` / 双方 `shooters` 一次性交给算法 | 拆成 `public_state.json` + `reveal_state.json`，public 不含任何隐藏信息 | `input-protocol` |
| 2 | preflight 用**与比赛相同的种子**生成地图并运行双方算法 | 改用 `matchId` 派生的 decoy 种子，撞车自动换种 | `preflight-decoy` |
| 3 | `judgeStartRound()` 只写日志，不改 phase、不置 flag，可被绕过 | START 成为硬门禁：未 START 直接 `computeRound()` 抛错 | `stage-gating`、`pre-start-execution` |
| 4 | A/B 载荷唯一差异是 `team_id`，两份输入不字节级相同 | 两份 JSON 逐字节相同，队别只经 `--team` argv | `roundstate-equality`、`input-protocol` |

## 3. 冻结的输入契约（规范 §4/§5/§8/§11/§12/§13/§20）

实现文件：`src/core/InputProtocol.ts`（唯一序列化入口）。

**`public_state.json`** —— 揭盲前可见的世界，**不含** obstacles / seed / shooter：

```json
{"schema_version":"1.1","match_id":"M-1","round":4,"map":{"xmin":-20,"xmax":20,"ymin":-12,"ymax":12},"points":[{"id":"A1","team":"A","x":-14,"y":6,"alive":true}]}
```

**`reveal_state.json`** —— 增量，只补隐藏信息：

```json
{"schema_version":"1.1","match_id":"M-1","round":4,"public_state_sha256":"92fa…","shooters":{"A":"A4","B":"B2"},"obstacles":[{"id":"O1","type":"rectangle","xmin":-1,"xmax":2,"ymin":-5,"ymax":1}]}
```

要点：

- **序列化是手写有序拼接**（固定键序、单行、无尾随换行、UTF-8），数值沿用既有 `num()` 约定
  （`-0` → `0`）。不依赖 `JSON.stringify` 的键序，也不受其数值格式影响。
- `points` 按引擎自然序（A1..An 再 B1..Bm），**含死点**（`alive: false`，规范 §5）。
- `map` 由 `Rules.ts` 的 `FIELD` 派生，单一数值来源。
- `sha256` 覆盖**文件的确切字节**，故 `sha256(file)` 等于字段值，可用 `shasum -a 256` 独立复核。
- `roundStateHash = sha256(publicStateSha256 + revealStateSha256)`（规范 §20），写入日志与回放。
- `verifyRevealBinding()` 重算 public 的 sha256 并与 reveal 内的 `public_state_sha256` 比对，
  拒绝「Round N public + Round N+1 reveal」错配（规范 §10）。
- 障碍物只序列化 `rectangle`（原样 + `id`）与 `circle`（`center:[x,y]` → `cx,cy,radius`，规范 §8）；
  出现 `segment` / `polygon` 时 `buildRevealState` **抛错**，防止静默产出规范外字段。
- **队别只经 `--team A|B`**（规范 §12）；两份 JSON 对双方逐字节相同（规范 §11），
  由 `tests/input-protocol.ts` 的 A/B 字节级比对用例守住。

入口契约（规范 §13）：

```bash
python solver.py --team A --public /input/public_state.json --reveal /input/reveal_state.json
```

## 4. 三段式编排（规范 §3/§17/§18/§19/§25/§26）

`MatchEngine` 的 `runRound()` 拆成四段，**`runRound()` 保留为顺序调用的兼容壳**：

```ts
beginRound():       { round, publicStateHash }   // PRE-REVEAL：生成 public_state.json
revealRound():      { revealStateHash, roundStateHash }  // REVEAL：双方 LOCK 后生成 delta
judgeStartRound():  { ok, error }                // START：真门禁，置 startGranted
computeRound():     Promise<RoundResult>         // 冻结字节 → 写文件 → runDuel
```

- **硬门禁**：`computeRound()` 在 `!startGranted` 时抛 `MatchEngineError`
  （「START 尚未下达 —— START 前参赛代码绝不运行（规范 §14/§15）」）。
- `startGranted` 只对本轮有效：结算后重置，新一轮必须重新 START。
- `beginRound()` / `revealRound()` 幂等；同一轮重复调用返回同一份字节（用例 5）。

`RoundMachine`（`src/core/Round.ts`）阶段集合 19 项不变，**转换表按规范 §25/§18 重排**：

```text
V1.0：WAITING_FOR_JUDGE → START_ROUND → COUNTDOWN → REVEAL → SEND_ROUND_STATE   （揭盲在 START 之后，与规范矛盾）
V1.1：WAITING_FOR_JUDGE → REVEAL → START_ROUND → COUNTDOWN → SEND_ROUND_STATE   （LOCK → REVEAL → START）
```

`tickCountdown()` 归零时不再自行转换（推进权交给宿主随后调 `sendRoundState()`），
保留规范 §18 的「START 后 3-2-1 GO」节奏。`lockShooter()` 现在同步驱动状态机，
使机器阶段与现场人工操作一一对应。

**冻结语义（规范 §19）**：`computeRound()` 内一次性快照 public/reveal 字节并写盘，
之后任何击杀都只走 `ShotCancelled`，**不重新生成 JSON**；日志中的三元哈希就是 START 前
生成的那一份（用例 4 硬断言）。

终端呈现（规范 §26）：

```text
PRE-REVEAL 板（points / 坐标 / alive，无 obstacles / shooter / seed）
   → 双方选点 → LOCK
REVEAL 板（Shooter id + 障碍物 + A/B ALGORITHM: NOT STARTED + [ START ]）
   → WAITING FOR JUDGE  ← 现场可停任意久，算法一行未跑
   → 回车 → START → 「TEAM A COMPUTING… / TEAM B COMPUTING…」→ ROUND RESULT
```

`--auto` 跳过两处等待。相关 UI：`AudienceScreenUI.renderPreRevealBoard()` /
`renderRevealBoard()`、`JudgeControllerUI.renderWaitingForStart()`。

## 5. Runner 与沙箱三区（规范 §23）

| 项 | V1.0 | V1.1 |
|---|---|---|
| 输入 | stdin 一行 JSON | `<sandbox>/input/public_state.json` + `reveal_state.json`（0444，宿主写入） |
| 包目录 | `<sandboxDir>/pkg` | `<sandboxDir>/app` |
| argv | `<bootstrap.py> <pkg/entry>` | `<bootstrap.py> <app/entry> --team A\|B --public <abs> --reveal <abs>` |
| bootstrap | 读 payload → READY → 等 GO → 回灌 stdin | 只等 `GO`；收到后 `sys.argv = [entry] + argv[2:]` 再 `runpy` |

- 沙箱内三区：`app/`（只读包）、`input/`（只读两份 JSON）、`work/`（**唯一**可写）。
- **SBPL 无需改动**：`input/`、`app/` 都在 `sandboxDir` 内，已被
  `(allow file-read* (subpath sandboxDir))` 覆盖；写权限仍只有 `work`。
  0444 是纵深防御，不是唯一屏障。
- **计时语义不变**：`release()` 仍是各队自己的 `releaseNs`，`computeTimeMs` 与超时从
  **各自 GO 写入**起算。预热解释器只消除解释器冷启动抖动，不改变计时锚点。
- `GB_TEAM` env 保留为冗余通道（`tests/process-tree-cleanup.ts` 已断言）。
- 顺带清理 V1.0 遗留 R-1：`SandboxRunner.ts` 中「共享 release 时刻」的过时注释已修正。

## 6. decoy preflight（规范 §14/§15/§16）

preflight 是参赛代码**真正会跑**的窗口，因此它绝不能拿比赛种子生成地图 ——
否则算法可以在 START 之前通过自己的运行环境反推出本轮障碍物。

- decoy 种子 = `derivePreflightSeed(matchId)` = `sha256(matchId + "|preflight")` 前 8 字节对 1e9 取模；
- 若与操作员 `--seed` 撞车，或与**地图生成器微调后的实际用种**撞车，自动换下一个候选（最多 8 次）；
- `preflight()` 返回值与审计日志记录 `decoySeed` / `decoyMapSeed` / `decoyMapHash` / `matchSeed`，
  可事后证明两个世界不同；
- decoy 世界的 `round` 仍为 `0`，`tests/hostile-input.ts` 用 `round == 0` 区分 preflight 与正式回合的门控不变；
- preflight 走**同一套两阶段协议**，因此同时充当新契约的端到端冒烟。

## 7. 日志与回放（规范 §19/§20）

- `RoundLog`：**移除** `stateHash`，新增 `publicStateHash` / `revealStateHash` / `roundStateHash`。
  （移除而非别名，避免审计时出现两个语义含混的「state hash」。）
- `ReplayFrame`：`stateHash` → `roundStateHash`，并新增 `publicStateHash` / `revealStateHash`。
- `MatchLog`：新增 `protocolVersion: '1.1'`；`schemaVersion` 保持 `1`（日志形状未变）。
- 回放仍**不包含** public/reveal 文件正文（只存哈希），`tests/replay.ts` 的禁含断言保留。
