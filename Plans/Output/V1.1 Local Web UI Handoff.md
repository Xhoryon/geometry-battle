## 1. 做了什么

把已经稳定的 Engine / Judge / Replay 包装成 `npm run app` 一键启动的本地比赛应用：

```text
npm run app   → 构建前端 → 绑定 127.0.0.1:17800（占用则自动换端口）→ 自动打开浏览器
```

三条正式路由：

| 路由 | 用途 |
|---|---|
| `/judge` | 裁判台：载入算法 → Preflight → Match Setup → Arena 预览 → 揭晓 → START → 结算 → 轨迹动画 → kills/alive → round result → match result → 回放 → 审计 → 重置/下一场 |
| `/spectator` | 只读大屏：满屏 Arena + 固定 Emitter + Combat Points + Obstacles + Round + Compute status + 轨迹动画 + kills + alive counts + winner/draw/stalemate |
| `/replay/:matchId` | 用保存的 MatchLog / Audit / trajectory 重放真实比赛，**不重新运行任何算法** |

`npm run judge`（终端裁判台）**一字未改**，仍是等价 fallback。

## 2. 架构：视图投影服务端

```
web/  (React 19 + Vite 8 + Canvas 2D)
  /judge  /spectator  /replay/:matchId
  只做三件事：渲染 board、发命令、订阅推送
        │   REST = 用户操作        WS = 实时 board
src/server/  (ts-node，只读消费 src/core)
  protocol.ts   线上类型与消息名（零 node import，前后端共用）
  boards.ts     白名单投影 judgeBoard() / spectatorBoard() + snapshotDigest()
  session.ts    MatchSession —— 唯一持有 MatchEngine；命令串行化 + ticker
  replays.ts    已落盘回放的索引与加载（严格 matchId 校验 + 服务端路径映射）
  security.ts   Host / Origin / Content-Type 校验
  http.ts       路由 + 静态资源 + SPA fallback
  ws.ts         board 广播（topic = judge | spectator）
  open.ts / main.ts
```

### 2.1 两条结构性约束

**服务端不新增任何判定。** 每个命令都是对 `MatchEngine`（或终端裁判台共用的
`MatchSetupUI`）的一次调用；每个 board 字段都是引擎查询的拷贝。`src/server/` 内
没有任何命中 / 先手 / 击杀 / 胜负 / 僵持的计算。

**观众板是逐字段白名单。** `spectatorBoard()` 显式构造每一个字段，没被拷贝的字段
浏览器根本收不到。因此「大屏不泄漏开发者诊断」是传输层的结构性事实，
而不是一句需要人工维护的约定。

### 2.2 轨迹

- 服务端下发的是引擎 `ReplayFrame` 里**已判定、已截断**的轨迹，经 `downsampleTrajectory`
  降到 ≤ 240 点；
- **只在产生时推送一次**，绝不随 100ms ticker 重复广播；WS 连接建立时补推一次（重连恢复）；
  推送丢失时走 `GET /api/trajectory/:id` 恢复；
- 浏览器只做 **reveal 比例的逐帧揭示**，从不求值函数 —— 重新求值会画出一条穿过
  障碍物的曲线，而真实轨迹在第一次接触障碍物处就永久终止了。

## 4. 安全

只绑定 `127.0.0.1` 挡不住 **CSRF** 与 **DNS rebinding** —— 那些请求确实来自本机。
因此命令通道有三道闸：

1. **Host 白名单**：`127.0.0.1:<port>` / `localhost:<port>` / `[::1]:<port>`，否则 403；
2. **Origin 必须缺席或同源**，否则 403（缺席放行：非浏览器客户端本来就不发 Origin，
   而攻击面恰恰是「浏览器会自动带 Origin」这个行为）；
3. **POST 必须是 `application/json`**，令跨站表单无法直接提交；不出 CORS 响应头。

WS upgrade **不经过** http 请求管线，因此走同一套 Host / Origin 校验 ——
否则一个恶意网页可以直接开一条直通裁判 topic 的信道。

`replay` 的 `matchId` 是唯一会长进文件路径的用户输入，经过三道：
字符白名单（`^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`，不许以 `.` 开头）→
**枚举命中**（路径从服务端 `readdir` 出的集合里选，从来不拼）→ resolve 复核。
未命中一律 404，且不区分「格式非法」与「不存在」。

### 5.2 套件覆盖了什么

**`web-projection`（20）** —— 纯函数层：
观众板顶层键与允许清单**逐字相同**（多一个键即失败）、观众板无禁用键、无绝对路径、
比赛未结束不得提前公布判决、摘要稳定 / 随比赛与轨迹句柄变化、
投影四角与单调性、四种障碍物投影、揭示语义（比例 0 至少 1 点 / 比例 1 完整 /
只做前缀切片不重采样）、降采样保留首尾、topic 校验。

**`web-server`（18）** —— 真 HTTP + 真 WS + 真算法：
- 完整链路：装两队 → 校验 → 开赛 → 手动两轮 → 后台跑完 → 终局 → 回放 → 重置 → 第二场；
- **每一步都先断言 board 标记 `enabled` 再执行，且执行不得失败** ——
  这是「UI 不许再猜一套规则」的机器化守卫：服务端启用判据与引擎真实门禁不一致就会红；
- 观众通道在真实对局结束后仍无禁用键、无绝对路径（并带**反空转对照**：
  裁判板本该含 `hash`/`audit`/`slots`/`runtime`）；
- 同一轨迹 id 恰好推送一次，且条数等于回合数；
- 轨迹点全部落在场地内（越界即说明它不是引擎给的）；
- 观众通道能观察到 `COMPUTING`；
- 伪造 Host → 403、跨源 POST → 403、跨源 WS upgrade → 拒绝、非 JSON 体 → 415、
  越权 matchId 一律被拒且不透露路径（映射层另有精确断言 + 正向对照）、
  未知接口 → 404、未知方法 → 405、坏 JSON 不回堆栈。

**`web/e2e/tournament.spec.ts`（Playwright）** —— 真浏览器完整演练：
启动服务 → `/judge` 载入两队 → Preflight → Match → 手动两轮 → 跑完余下 → 终局
→ `/spectator`（断言无任何按钮、无任何诊断字样）→ `/replay/:matchId` → 重置
→ 第二场（只用「使用槽位算法」）→ 全程无页面级 JS 错误。

## 6. 施工中改掉的两处设计

**(1) `run-to-end` 从「阻塞请求」改成后台任务。** 原设计让 HTTP 请求挂到比赛结束 ——
一场最长 60 轮，那是分钟级请求，浏览器与 undici 都有超时，现场也不该「点一下然后转圈」。
改成后台推进 + board 上暴露 `busy`，进度靠 WS 推的 board 看。

**(2) Content-Type 校验只作用于 POST。** 原先对所有非 GET 方法要求 JSON 体，
于是 `PUT /api/health` 回 415 而不是 405 —— 把纯路由问题报成了协议问题。

## 7. 施工中抓到的九个真问题

**(1) 越权测试的「全 null」是假绿。** `resolveMatchDir` 的越权用例一开始全绿 ——
因为我传错了根目录（tmp 根而非 `artifactRoot`），于是**所有** id 都解析为 null。
加了「真实存在的 matchId 必须解析得到」的正向对照才暴露。
**教训：只断言「全部被拒绝」的用例，在实现整体坏掉时也是绿的。**

**(2) 观众板对照断言测的是空集合。** `collectKeys` 的闭包捕获了外层集合，
传入裁判板后仍写进同一个 Set，对照集合永远为空。同样靠反空转对照抓出来。

**(3) URL 规范化会吃掉 `..`。** `GET /api/replays/../../etc/passwd` 被 `new URL()`
规范化成 `/etc/passwd`，落到静态处理器（同样被拒），回不到 replay 路由的 404。
不是漏洞，但说明「用某个具体状态码断言越权」是脆的 —— 改成断言
「绝不成功 + 绝不透露路径」，并在映射层做精确断言。

**(4) 命中闪是死代码。** 白热环画在「存活 / 阵亡」分支**之后**，而本轮被打死的点
在这张板上已经是 `alive: false` —— 于是它永远画不出来，签名视觉线索成了装饰。
修复：移到分支之外，并给它一个**衰减窗口**（轨迹走完后再闪 900ms 后归零）——
常驻的「刚刚命中」到了下一轮就是在说谎。

**(5) board 把 `aHits` 当成了击杀列表。** `aHits` 是**命中**列表：双方同时开火时，
后手方可能命中一个已被对手击杀的点。终端裁判台那行也用了同一个表达式
（未改动终端）。Web 侧改用权威来源 `ReplayFrame.killed`（引擎结算时定死的集合）。

**(6) 源文件里混进了一个字面 NUL 字节。** 一个恶意测试样本 `'nul byte'` 里
实际是一个 NUL 字符。它让 `file` 报 `data`、`grep` 把整个文件当二进制跳过 ——
**基于文本的证据链工具全部失效**（本轮正是靠 grep 找不到 `src/server` 才发现的）。
修复：源文件里改写成**转义形式**（`'nul\u0000byte'`），字符串的**值**一个字符没变，但源文件回到纯文本。
随后逐文件复检了全部新增源文件均为 text。

**(7) `<details>` 的展开判断用错了属性。** `getAttribute('open')` 在**已展开**时返回
空串（falsy），取反会把展开的区域又点回收起。改用 DOM 上的 `open` 属性。

**(8) 在 render 里改 history。** `App.tsx` 的 `/` → `/judge` 规范化原本写在渲染分支里，
改 history 是副作用，移到 effect。

**(9) 死代码。** `web/src/api/client.ts` 的 `useCommand` 无人引用，已移除。

## 8. 一次未复现的耗时异常（如实记录）

同一份代码，浏览器演练出现过一次 **14.8 分钟**（其余次均为 7–10 秒），
且**比赛内容完全相同**（seed 700001 下 3 回合 MUTUAL_ELIMINATION、每轮 25–36ms）。
即：慢的**不在比赛**，而在某一步等待上；耗时紧贴 15 分钟的测试上限。

我**没有**查明原因。当时机器刚从一次被我中断的全量回归中恢复
（`pkill` 后残留的沙箱进程可能仍在抢 CPU），事后无法回溯证实。
之后三次重跑均为 8 秒左右。

为此加了一个永久的改进：演练现在自带 `StepClock` 分段计时（见 §5.3）。
若该现象复现，分段耗时能直接指出卡在哪一步 —— 这比继续猜有用。
